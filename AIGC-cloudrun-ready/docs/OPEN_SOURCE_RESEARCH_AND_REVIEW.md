# 织梦学旅：开源项目调研、产品评估与工程建议

> 调研时间：2026-09-01  
> 评估基线：当前仓库源码与《项目功能与架构全景》  
> 调研范围：任务游戏化、生产力/习惯养成、学习复习、Agent 记忆与工作流、多用户任务后端、微信小程序工程化。

## 1. 结论先行

织梦学旅当前最有辨识度的不是“AI 自动生成任务”，而是这条组合链路：

**长期目标 → 今日可执行动作 → 专注完成 → 冒险叙事 → 星图收集 → 可帮助下一次行动的道具。**

这条链路已经比普通 TODO Demo 更完整，尤其是“星图道具反过来帮助真实任务”的设计，具备继续打磨的价值。但当前项目同时承载了任务管理、AI 规划、角色成长、记忆、星图、商店和副本，产品表面积已经超过比赛版团队通常能够稳定验证的范围。

综合用户价值和工程风险，建议下一阶段不要继续横向增加玩法，而应围绕三个问题收敛：

1. **用户今天到底该做什么**：建立跨目标的全局每日容量，避免每增加一个目标就机械增加 5 个任务。
2. **用户为什么相信计划**：让用户确认计划、反馈难度和调整节奏，AI 给建议，用户保有决定权。
3. **系统能否安全地服务多用户**：先完成用户级鉴权、数据库和单一目标模型，再谈长期 Agent 和记忆升级。

建议的产品定位是：

> 面向有明确阶段性学习目标、但难以稳定执行的学生，用 AI 把目标转成低压力的每日行动，并通过可持续的冒险反馈帮助其坚持。

暂时不建议把产品定义成“通用自律平台”或“完整 RPG”。越泛化，AI 规划质量、内容成本和页面复杂度越难控制。

## 2. 开源项目调研

### 2.1 Habitica：任务游戏化的完整样本

项目：[HabitRPG/habitica](https://github.com/HabitRPG/habitica)  
定位：将现实目标包装成 RPG，成功行动带来升级和金币，失败会损失生命值。

值得参考：

- 游戏反馈和现实任务存在清晰的一一映射；
- 奖励货币、装备和角色成长形成长期反馈；
- 任务数据与游戏结算分离，先有真实行动，再有游戏反馈；
- 有足够长的运营历史，可以观察复杂经济、社交和任务系统带来的维护成本。

对织梦学旅的启示：

- 当前“主线星 → 星图 → 道具 → 帮助任务”的闭环方向正确，比单纯经验值更有功能意义；
- 不应照搬惩罚性生命值。学习产品中，错过一天如果导致强烈损失，容易让已经中断的用户彻底放弃；
- 不应在现阶段复制公会、社交、复杂装备和多货币。Habitica 的规模证明这些系统可行，也同时说明其工程与运营成本很高；
- 游戏层要快速反馈，不能让用户为了完成一个任务连续阅读多段剧情和弹窗。

可直接落地的做法：把奖励拆为“立即反馈”和“长期收藏”。任务完成后先用 1—2 秒完成结算，详细剧情允许稍后在日志中阅读。

### 2.2 Super Productivity：执行效率比玩法丰富更重要

项目：[super-productivity/super-productivity](https://github.com/super-productivity/super-productivity)  
定位：集成 Timeboxing、时间跟踪、番茄钟、休息提醒、个人指标和外部任务源的本地优先生产力工具。

值得参考：

- 今日任务、预计时间、实际时间和休息提醒形成完整执行闭环；
- 支持子任务、项目、标签和上下文信息，但核心操作仍围绕“开始/停止当前任务”；
- 提供个人指标，让用户根据真实执行记录调整计划；
- 明确强调本地优先、数据归属和同步选择；
- 仓库内维护架构决策、E2E、文档和多端构建，是工程治理的成熟样本。

对织梦学旅的启示：

- 当前专注计时仅保存在前端页面，缺少暂停、恢复、实际投入时长和中断原因；
- 预计时长不应只是装饰字段，应成为次日计划调整的依据；
- “今日只选最重要的少量任务”比每个目标固定释放 5 项更符合用户认知；
- 可以先做周报中的“计划分钟 / 实际分钟 / 完成率 / 被调轻次数”，而不是继续增加虚拟数值。

### 2.3 Loop Habit Tracker：柔性坚持而非连续天数绑架

项目：[iSoron/uhabits](https://github.com/iSoron/uhabits)  
定位：轻量、离线、重隐私的长期习惯应用。

值得参考：

- Habit Score 会随重复逐步增强、随中断逐步减弱，而不是一天中断就把全部进度清零；
- 支持每周数次、隔日等灵活计划，不强制所有习惯每天执行；
- 提醒、Widget 和快速勾选降低回到应用的成本；
- 支持 CSV/SQLite 导出，让用户掌控自己的数据；
- 核心界面保持轻量，长期数据通过图表和统计逐步展开。

对织梦学旅的启示：

- 当前 `streak` 是单一连续天数，并且新用户从 4 天开始，会削弱数据可信度；
- 长期目标应支持“每周 3 天”“周末休息”“考试前加量”等节奏，而不是统一每日发布；
- 应提供“休息日/跳过且不惩罚/身体不适”状态；
- 对中断用户应突出“从一个 5 分钟动作恢复”，不应强调失去连击。

### 2.4 Anki 与 FSRS：复习必须基于反馈，而不是固定日期

项目：[ankitects/anki](https://github.com/ankitects/anki)、[open-spaced-repetition/fsrs4anki](https://github.com/open-spaced-repetition/fsrs4anki)  
定位：Anki 是成熟的间隔重复系统；FSRS 将复习历史建模为难度、稳定性和可提取性，并用反馈优化复习间隔。

值得参考：

- 复习对象有独立状态，不等同于普通 TODO；
- 用户反馈 `Again / Hard / Good / Easy` 会改变下一次间隔；
- 调度器和参数优化器分离，可验证、可替换；
- 复习记录本身是后续调度的依据。

对织梦学旅的启示：

- 当前“记忆符印”固定安排第 1、3、7 天复习，适合作为 MVP，但不能宣称个性化记忆算法；
- 如果要升级，应先把任务产物转成“可复习对象”，例如知识点、错题、词汇或一段用户总结；
- 每次复习至少收集“忘记/困难/掌握”反馈，再动态调整间隔；
- 不建议现在直接嵌入完整 FSRS。数据量不足时，用简化的反馈驱动状态机更易解释和验证。

### 2.5 Mem0：记忆需要命名空间、检索和评估

项目：[mem0ai/mem0](https://github.com/mem0ai/mem0)  
定位：面向 AI Agent 的持久记忆层，区分用户、会话和 Agent，并支持语义、关键词、实体和时间信号组合检索。

值得参考：

- 明确以 `user_id / agent_id / run_id` 隔离记忆；
- 记忆拥有新增、检索、更新、删除和历史 API，而不是只拼接到一个 Markdown 文件；
- 通过实体关联、时间推理和多信号检索选择真正相关的记忆；
- 提供公开的记忆评测框架，强调“能否取回正确记忆”，而不是只看保存数量；
- 自托管服务默认开启认证，说明记忆数据需要和普通业务数据同等级保护。

对织梦学旅的启示：

- 现有 L1/L2/L3 分层思路是合理的，MVP 暂时没有必要引入向量数据库；
- 当用户记忆超过几十/几百条后，应从“最近 8 条全带入”升级为按当前目标、阶段、实体和时间检索；
- 记忆必须绑定用户和目标，不能继续依赖进程中的全局当前 Agent；
- 应给用户查看、纠正和删除记忆的能力，尤其是 AI 生成的“世界实体”和用户画像。

### 2.6 LangGraph.js：借鉴可恢复工作流，不必马上引入框架

项目：[langchain-ai/langgraphjs](https://github.com/langchain-ai/langgraphjs)  
定位：用于构建可控、持久、可恢复、可人工介入的状态型 Agent 工作流。

值得参考：

- 每一步有明确 State 输入输出，而不是在长函数中修改大量全局字段；
- Durable Execution 允许失败后从检查点继续；
- Human-in-the-loop 可以在执行中审核或修改 AI 结果；
- 通过轨迹和状态转换观察 Agent 失败在哪里。

对织梦学旅的启示：

- 初始化链路“蓝图 → 阶段 → 滚动任务 → 保存账号”适合改为显式工作流和检查点；
- 用户确认 AI 计划就是最有价值的 Human-in-the-loop 节点；
- 应记录 Prompt 版本、模型、耗时、降级原因和输出校验结果；
- 当前业务流程大多是确定性状态机，直接引入 LangGraph 可能增加依赖和认知成本。先在现有代码中实现显式 Command/State Transition，复杂度真的增长后再评估框架。

### 2.7 Vikunja：多用户任务系统的工程边界

项目：[go-vikunja/vikunja](https://github.com/go-vikunja/vikunja)  
定位：可自托管的任务管理服务。

值得参考：

- 仓库明确分离 `frontend`、`rest`、领域包和部署资产；
- 任务系统围绕用户所有权、项目/列表、权限和稳定 API 建模；
- 有正式的安全报告入口、安装、测试和开发文档；
- 支持自托管场景，工程设计围绕持久数据和升级演进，而不是单一运行时快照。

对织梦学旅的启示：

- 当前最需要学习的不是 Vikunja 的全部功能，而是“每一条目标/任务/记忆都明确属于哪个用户”；
- 应建立 Repository 层和关系型数据库，让业务服务不再知道 JSON 文件路径；
- API 需要用户上下文、分页、资源级权限和正确的 HTTP 状态码；
- 数据迁移应成为显式版本化流程，而不是每次读取全量状态时顺带修复。

### 2.8 微信小程序与 CloudBase 官方示例：认证和 CI 不应缺席

项目：[wechat-miniprogram/miniprogram-demo](https://github.com/wechat-miniprogram/miniprogram-demo)、[wechat-miniprogram/api-typings](https://github.com/wechat-miniprogram/api-typings)、[TencentCloudBase/cloudbase-skills](https://github.com/TencentCloudBase/cloudbase-skills)

值得参考：

- 官方类型明确了 `callContainer` 的服务、环境、超时、返回状态和 Call ID；
- CloudBase 示例把数据库集合权限区分为公开读、创建者写、仅创建者读写和仅管理员读写；
- 官方工程指引要求校验真实 `miniprogramRoot`、AppID、云环境和发布路径；
- 小程序 CI 可以自动完成构建、预览和上传，私钥必须放在 CI Secret 中。

对织梦学旅的启示：

- 继续保留统一 `services/api.js` 是正确的，但应补超时、请求 ID、环境区分和错误码；
- 不能只靠“本机 userId”判断登录，服务端必须从可信身份获取用户上下文；
- 应加入小程序预览/上传流水线，并使用开发、测试、生产三个配置环境；
- 外层与内层两份 `project.config.json` 容易导入错误，应统一项目根。

## 3. 可借鉴项优先级

| 参考项目 | 建议借鉴 | 当前是否值得引入 | 理由 |
| --- | --- | --- | --- |
| Habitica | 行动—奖励映射、收藏反馈 | 高 | 与现有星图闭环直接吻合 |
| Super Productivity | Timeboxing、实际时长、周统计、休息 | 高 | 能直接改善每日执行价值 |
| Loop | 柔性计划、温和连续性、提醒、导出 | 高 | 解决中断和固定每日任务压力 |
| Anki/FSRS | 反馈驱动复习状态 | 中 | 先有知识对象与反馈，再上算法 |
| Mem0 | 用户/会话/Agent 隔离、检索评测 | 中低 | 先修多用户数据模型，暂不急于向量化 |
| LangGraph.js | 检查点、人工确认、轨迹 | 中低 | 借思想即可，当前不必增加框架 |
| Vikunja | 用户所有权、Repository、迁移、API | 很高 | 是当前服务走向可用产品的基础 |
| 微信/CloudBase 示例 | 身份、权限、CI、多环境 | 很高 | 与实际部署平台直接相关 |

## 4. 用户需求角度评估

### 4.1 目标用户是否明确

当前最匹配的用户是：

- 有考试、课程、作品集等 2—12 周明确目标；
- 知道目标重要，但不擅长拆解和持续执行；
- 愿意接受轻度游戏化，但主要诉求仍是完成学习；
- 每天可投入 20—120 分钟的学生。

不建议当前同时服务：健身、生活习惯、复杂项目管理、职业协作和纯游戏用户。不同目标的任务质量标准、进度证据和复习机制完全不同，会迅速稀释产品价值。

### 4.2 当前用户价值评分

| 维度 | 评分 | 评价 |
| --- | --- | --- |
| 首次吸引力 | 4/5 | 角色、世界观和星图有展示效果，差异化明显 |
| 目标到行动 | 3/5 | 能生成具体任务，但用户缺少计划确认，多个目标会造成任务爆炸 |
| 今日执行效率 | 3/5 | 有专注、编辑和调轻；缺少暂停恢复、实际时间和全局优先级 |
| 长期坚持 | 3/5 | 星图收藏有动力；固定每日节奏、假初始连击和中断惩罚风险较大 |
| 学习有效性 | 2/5 | 记录的是“完成”，没有验证学习产物、回忆质量或错误修正 |
| 用户控制感 | 2.5/5 | 可编辑任务，但计划在初始化时直接生成并发布，AI 解释和确认不足 |
| 可信度 | 2.5/5 | 规则降级是优点；初始虚拟数据、AI 叙事和真实学习指标混在一起 |
| 数据与隐私 | 1.5/5 | 小程序不暴露模型 Key，但服务端缺少用户级鉴权和数据隔离 |

### 4.3 最关键的用户问题

#### 问题一：并行目标会放大压力

每个活动目标每天固定释放 3 主线 + 2 支线。用户有 3 个目标时会得到 15 个目标任务，再加自建任务和复习任务。产品原本要降低“我不知道做什么”的焦虑，反而可能制造新的任务债务。

建议：

- 用户设置的是“每天总投入”，系统必须先按全局容量选任务，再分配到目标；
- 默认每天只给 1 个必做、最多 2 个建议、其余放入候选；
- 并行目标需要优先级和每周频率，不应每个目标每天都运行；
- 今日全清不应成为默认成功标准，完成最重要的一项也应得到完整正反馈。

#### 问题二：AI 计划缺少协商过程

用户提交目标后，系统直接生成世界、阶段和任务。虽然结果页能看到初始任务，但缺少“这是否符合你的教材、基础和时间”的确认。

建议：

- 注册后先返回 3—5 个澄清问题，至少覆盖当前水平、资料、截止日、每周可用日和成功证据；
- 计划生成后让用户确认阶段和第一周任务，可编辑后再正式开始；
- 每周提供一次复盘：保留、调轻、加速或换方向；
- 每个 AI 建议附一行“为什么今天安排它”，但不要输出冗长模型推理。

#### 问题三：完成不等于学会

当前专注计时和完成接口只能证明用户点击了完成，不能证明学习结果。对于自律工具这可以接受，但页面中的“知识点掌握度”等文案容易让用户误以为系统在评估学习效果。

建议：

- 明确区分“执行完成率”和“学习掌握度”；没有证据时不展示掌握度；
- 为主线任务定义可选学习产物：一道答案、一段总结、错题照片、录音或自评；
- 用轻量的“困难 / 还行 / 熟练”自评驱动后续任务和复习；
- 先服务考试学习场景，才能定义相对稳定的验证方式。

#### 问题四：游戏反馈有遮挡核心操作的风险

初始化、任务创建、完成、建议和结算都会生成故事或弹窗。对首次演示很有吸引力，但日常使用中会增加完成任务的步骤。

建议：

- 用户完成任务后先立即打勾和结算，剧情卡片可展开或稍后阅读；
- 提供“轻叙事/完整叙事”偏好；
- 把长剧情集中到每日/每周章节，不必每个小动作都调用模型；
- 统计用户是否跳过剧情，以真实行为决定叙事频率。

#### 问题五：恢复机制弱于连续机制

对真正有拖延问题的用户，最重要的不是连续 30 天，而是中断两天后愿意回来。当前系统有 5 分钟保底道具，但它被锁在完成星图后的奖励中，最需要它的新用户反而拿不到。

建议：

- 把“5 分钟保底行动”做成基础能力，道具只提供更强版本；
- 连续中断后自动进入恢复模式：只给一个最小动作；
- 将 streak 改为温和的“节奏分”，错过一天缓慢下降；
- 允许计划休息日，休息不等于失败。

## 5. 软件工程角度评估

### 5.1 当前工程优点

1. **AI 可降级**：没有 DeepSeek Key 时核心链路仍可运行，业务没有被模型完全绑架。
2. **确定性结算**：奖励、星图、道具和副本资格由后端规则决定，AI 只负责内容生成。
3. **统一 API 边界**：小程序只通过 `services/api.js` 访问后端，后端通过 DTO 转换内部状态。
4. **配置驱动角色**：角色和技能使用 Front-matter + Markdown，策划内容和业务代码有一定分离。
5. **已有回归测试**：覆盖每日幂等、并行目标、滚动规划质量、星图奖励和副本防重。
6. **状态迁移意识**：Store 带版本和旧数据修复逻辑，说明项目已经考虑演进。
7. **依赖简单**：原生 Node 后端容易启动、容器化和比赛演示。

### 5.2 当前工程风险评分

| 维度 | 评分 | 主要问题 |
| --- | --- | --- |
| 模块边界 | 2.5/5 | `sessionService.js` 超过 4000 行，账号、规划、任务、星图、副本和迁移集中在同一聚合根 |
| 数据一致性 | 2/5 | 全局可变状态 + 同步文件写入，无事务、并发控制和幂等键 |

| 可测试性 | 3/5 | 领域回归不错，但缺少 API 契约、并发、鉴权、E2E 和失败注入 |
| 可观测性 | 1.5/5 | 缺少结构化日志、请求 ID、模型耗时/成本、降级率和错误分类 |

### 5.3 最需要先解决的工程问题

#### P0：建立真正的用户隔离

建议的数据主键关系：

```text
users
  └─ goals
      ├─ phases
      ├─ daily_plans
      │   └─ task_instances
      ├─ task_templates / goal_nodes
      └─ review_items
  ├─ agent_profiles
  ├─ memories
  ├─ diary_entries
  ├─ inventories
  └─ dungeon_runs
```

所有 Repository 方法必须显式接收 `userId`，不能通过“当前全局账号”隐式决定数据归属。使用微信可信身份或服务端会话令牌，密码登录若继续保留则改为 Argon2id/bcrypt/scrypt。

#### P0：统一 `goalPlan` 和 `goalPortfolio`

目前两个目标模型同时控制不同能力：Portfolio 控制当前星图任务，旧 GoalPlan 控制阶段终章和副本。副本测试已经暴露 `LONG_TERM` 与 `STAGE` 口径不一致。

建议以 Portfolio Goal 为唯一聚合根：

- `Goal` 保存目标、期限、优先级、频率和状态；
- `Phase` 保存阶段；
- `GoalNode` 保存规划任务模板/星位；
- `TaskInstance` 保存某天真正发布给用户的任务；
- 章节、星图和副本都读取同一 Goal/Phase/TaskInstance。

#### P0：把文件 Store 替换为 Repository + 数据库

不要直接在 `sessionService` 中把 JSON 改成 SQL。先定义 Repository 接口，再实现数据库适配器：

- `UserRepository`
- `GoalRepository`
- `DailyPlanRepository`
- `TaskRepository`
- `MemoryRepository`
- `RewardLedgerRepository`

任务完成、奖励、星位点亮和道具发放必须在一个数据库事务中提交。对完成、购买和副本结算接口加入 `Idempotency-Key` 或唯一业务约束。

#### P1：拆分应用服务

建议把 `sessionService.js` 拆为：

- `AccountApplicationService`
- `GoalPlanningApplicationService`
- `DailyPlanningApplicationService`
- `TaskCompletionApplicationService`
- `StarMapApplicationService`
- `DungeonApplicationService`
- `AgentNarrativeApplicationService`
- `LegacyMigrationService`

每个 Command 返回 `{ event, stateDelta }` 或领域事件，由事务边界统一保存。查询和命令分开，避免 `GET /sessions/current` 在读取时执行大量迁移和写入。

#### P1：补齐 AI 可靠性

- 使用 JSON Schema/Ajv 校验模型输出，不只依赖手写 normalize；
- 给 fetch 增加超时和 AbortController；
- 对 429/5xx 做有限指数退避，不对业务校验错误重试；
- 记录 `promptVersion/model/latency/tokenUsage/fallbackReason`；
- 建立 20—50 个固定目标的规划评测集，检查具体度、总时长、重复、前置依赖和安全性；
- 缓存相同目标模板，降低初始化等待和模型成本。

#### P1：建立 CI/CD 和可观测性

每次提交至少执行：

1. 后端语法/Lint/单元测试；
2. API 契约和数据库迁移测试；
3. 小程序静态校验；
4. 小程序关键路径自动化或模拟测试；
5. Docker 构建与健康检查；
6. 预览二维码产物，主分支才允许上传测试版。

运行时使用结构化日志，并贯穿 `requestId/userId/commandId/goalId/taskId/llmRunId`。重点指标包括计划生成成功率、降级率、P95 延迟、任务接受率、任务调轻率、次日回访和 7 日目标留存。

## 6. 推荐产品方案

### 6.1 MVP 应保留的核心

- 三种角色与轻量世界观；
- 一个主目标，可选一个次目标；
- 用户确认后的阶段计划；
- 每日全局 1 必做 + 最多 2 建议；
- 专注、完成、调轻、恢复；
- 主线星与星图收藏；
- 每日简短故事、每周完整章节；
- 基于完成反馈的复习任务；
- 周复盘和节奏调整。

### 6.2 建议暂时隐藏或删除

- 未接入的商店；
- 未接通且读取旧模型的夜间副本；
- 复杂副本数值面板；
- 没有真实依据的“知识掌握度”；
- 新用户预置的 4 天连击、58 成长、92 资源；
- 同时存在的两套长期目标完成逻辑。

“隐藏”不等于永久放弃。先让核心 7 日学习闭环可验证，再根据用户是否真的需要玩法决定恢复。

### 6.3 建议的新用户流程

```text
输入目标
  → 回答 3—5 个澄清问题
  → 查看并编辑阶段 + 第一周计划
  → 选择每天总容量和每周休息日
  → 开始今天唯一的必做任务
  → 快速完成反馈
  → 可选阅读故事
  → 晚间简短复盘
  → 每周重新确认节奏
```

角色选择可放在目标之后，或提供默认角色直接开始，减少首次价值到达时间。

## 7. 分阶段路线图

### 第一阶段：两周内，收敛与修正

- 统一产品定位和核心用户；
- 删除假初始成长数据；
- 将每日任务改为全局容量调度；
- 提供计划确认、休息日和 5 分钟恢复模式；
- 隐藏商店和副本入口/残留宣传；
- 修复副本测试或明确移除该模块；
- 建立最小用户研究：5—8 名学生完成 7 天试用。

成功标准：70% 用户能在 2 分钟内理解今天该做什么；首日计划接受率、首项任务启动率和次日回访率可被记录。

### 第二阶段：四到六周，工程可用化

- 微信身份/令牌鉴权；
- MySQL/PostgreSQL + Repository + 数据迁移；
- 统一 Goal/Phase/TaskInstance 模型；
- 任务完成、奖励和道具事务化、幂等化；
- 拆分 `sessionService`；
- 加入 AI 超时、Schema 校验、日志和评测集；
- 建立 CI、小程序测试版发布和基础监控。

成功标准：两个并发用户互不影响；容器重启不丢数据；重复完成请求不重复发奖励；AI 故障时稳定降级。

### 第三阶段：验证后再扩展

- 反馈驱动的复习对象与调度；
- 用户可查看、纠正和删除 Agent 记忆；
- 按目标/阶段/实体检索长期记忆；
- 根据真实使用数据决定恢复副本；
- 若复杂长任务确实需要断点恢复，再评估 LangGraph.js；
- 若记忆规模和检索质量成为瓶颈，再评估 Mem0 或自建混合检索。

## 8. 建议验证的用户假设

在继续大规模开发前，优先验证：

1. 用户是否愿意让 AI 安排第一周任务，还是只希望 AI 帮忙拆第一步？
2. 冒险叙事是否提高次日回访，还是只提高第一次使用的新鲜感？
3. 用户每天能接受几个任务？“1 必做 + 2 建议”是否优于固定 3+2？
4. 用户更在意星图收藏、角色成长，还是计划确实可执行？
5. 中断后，5 分钟恢复任务能否提高重新启动率？
6. 用户是否愿意提交总结/自评，用于更可靠的复习调度？

建议的北极星指标不是“生成了多少故事”，而是：

> **每周完成至少 3 次用户主动确认过的有效学习行动的人数比例。**

辅助指标：计划接受率、任务启动率、完成率、实际/预计时间偏差、调轻率、恢复率、7 日留存、AI 降级率和单活跃用户模型成本。

## 9. 最终建议

### 应立即做

1. 收敛到阶段性学习目标；
2. 以全局每日容量替代每目标固定 3+2；
3. 让用户确认并调整 AI 计划；
4. 去掉假数据和无法证明的掌握度；
5. 统一 GoalPlan/Portfolio；
6. 完成用户鉴权、数据库和事务；
7. 隐藏未接通的副本与商店，减少认知负担。

### 应继续保留

1. 角色配置驱动的叙事差异；
2. AI 故障时的规则降级；
3. 星图收藏与功能性道具；
4. 任务调轻和保底行动；
5. L1/L2/L3 记忆思想，但先不引入重型向量系统；
6. 后端确定性奖励裁决。

### 暂时不要做

1. 公会、排行榜、复杂商城和多货币；
2. 在没有用户反馈数据前接完整 FSRS；
3. 为了“Agent 感”直接引入 LangGraph；
4. 在没有多用户数据模型前接 Mem0/向量数据库；
5. 继续在 4000 行 `sessionService.js` 中叠加新玩法。

一句话判断：**项目值得继续，但下一轮的关键词应是“可信、轻量、可恢复、可隔离”，而不是“更多玩法”。**
